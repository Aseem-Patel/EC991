PART 3What a package is

Last week you made an environment: a folder with a Project.toml that lists the packages your code uses. A package is an environment that also contains code of its own, under a name you can load. Here the name is EC991Week2, and loading it takes one line:

using EC991Week2

After that line, every function the package exports is available: Household, asset_grid, solve_vfi, solve_backward and the rest. Three things make a folder a package:

  1. A Project.toml with a name and a uuid (Part 4).
  2. A file src/EC991Week2.jl, named after the package, that defines a module.
  3. The code that the module pulls in with include.

Here is the module file, src/EC991Week2.jl, without its opening comment:

module EC991Week2

include("household.jl")      # paste the contents of these files here,
include("grid.jl")           # in this order
include("bellman.jl")
include("vfi.jl")
include("backward.jl")
include("simulate.jl")
include("checks.jl")

export Household, utility, marginal_utility      # names visible after `using`
export asset_grid
export bellman_step!
export Solution, initial_guess, solve_vfi
export FiniteSolution, solve_backward
export simulate, simulate_finite
export euler_residuals, cake_eating_consumption, cake_eating_path, life_cycle_income

end
  • module ... end wraps everything in its own namespace, so the package's names cannot collide with yours.
  • include("file.jl") runs that file as if its text stood here. The files are in the order of the lab slides.
  • export lists the names you can use directly after using EC991Week2. Anything not exported is still reachable as EC991Week2.name, for example EC991Week2.nearest_index.

Why a package, and not one long script?

The same solver is used in three places: the scripts that make the slide figures, the tests that check it against theory, and the notebook. If each had its own copy of the double loop, a fix in one would not reach the others. With a package there is one copy, and everything else calls it. Every model in this course is organised this way, the Aiyagari model in week 5 included.

PART 6The code that does VFI

Four pieces, in the order they are used: the household, the grid, one Bellman step, and the loop that repeats it.

The household: one struct for five numbers

Base.@kwdef struct Household{T<:Real}
    β::T = 1 / 1.05   # discount factor
    R::T = 1.03       # gross interest rate, 1 + r
    y::T = 1.0        # constant income (wage normalised to one)
    ϕ::T = 0.02       # borrowing limit: a' ≥ -ϕ
    γ::T = 2.0        # CRRA curvature; γ = 1 is log
end

A struct bundles the parameters, so every function receives them together as hh. Base.@kwdef gives each field a default and lets you change one by name: Household() gives the defaults, and Household(β = 1/1.03) changes only $\beta$. The grid is one line: asset_grid(hh; amax = 3.0, na = 300) returns 300 evenly spaced points from $-\phi$ to $3$.

One Bellman step: bellman_step!

This is the double loop from the slides. For each state $a_i$ it tries every candidate $a'_k$ and keeps the best:

function bellman_step!(V1, pol, V0, hh::Household, a; y = hh.y)
    (; β, R) = hh                        # unpack two fields of hh
    na = length(a)
    for i in 1:na                        # state a_i
        best, kbest = -Inf, 0
        for k in 1:na                    # candidate a'_k
            c = R * a[i] + y - a[k]
            c <= 0 && continue           # infeasible: skip it
            v = utility(c, hh) + β * V0[k]   # the Bellman right-hand side
            if v > best
                best, kbest = v, k
            end
        end
        if kbest == 0                    # nothing feasible at all
            best, kbest = -Inf, 1
        end
        V1[i], pol[i] = best, kbest
    end
    return V1, pol
end
  • The ! in the name is a Julia convention: the function overwrites some of its arguments, here V1 and pol. It does not allocate new arrays on every call, which matters when it runs hundreds of times.
  • V0 is the input, the current guess. V1 is the output, the guess after one step. In the maths, $V_1 = T V_0$.
  • pol[i] stores the index $k$ of the best choice, an integer, not an asset level.
  • Income y is a keyword argument with default hh.y. The finite-horizon solver passes a different y at each date and reuses this function unchanged.

Iterating to the fixed point: solve_vfi

function solve_vfi(hh::Household, a; tol = 1e-6, maxiter = 2000)
    V0 = initial_guess(hh, a)                      # Step 2: u(ra + y) / (1 - β)
    V1 = similar(V0)
    pol = zeros(Int, length(a))
    distances = eltype(V0)[]
    for ℓ in 1:maxiter
        bellman_step!(V1, pol, V0, hh, a)          # Step 3: V1 = T V0
        d = maximum(abs(V1[i] - V0[i]) for i in eachindex(a))
        push!(distances, d)
        if d < tol                                 # Step 4: converged
            apol = a[pol]                          # policy: index → asset level
            cpol = hh.y .+ hh.R .* a .- apol       # policy: budget → consumption
            return Solution(a, copy(V1), copy(pol), apol, cpol, ℓ, distances)
        end
        V0, V1 = V1, V0                            # the update becomes the guess
    end
    error("value function iteration did not converge in $maxiter iterations")
end
  • Convergence is the sup-norm distance $d_\ell = \max_i |V_\ell(a_i) - V_{\ell-1}(a_i)|$. Every distance is stored, so you can plot it and check that it falls by at least the factor $\beta$ each step.
  • V0, V1 = V1, V0 swaps the two arrays, so the new value becomes the next guess without copying anything.
  • The policy functions come out of the last step for free. pol already holds the maximising index at every state. a[pol] turns indices into asset levels, $a'(a_i)$. The budget constraint then gives consumption, $c(a_i) = y + R a_i - a'(a_i)$. The dots in .+ and .* apply the operation to every element of the vector.
  • Everything is returned in one Solution struct with fields a, V, pol, apol, cpol, iterations and distances.

Using it

using EC991Week2
hh  = Household()                      # β = 1/1.05, R = 1.03, so βR < 1
a   = asset_grid(hh; amax = 3.0, na = 300)
sol = solve_vfi(hh, a)
sol.iterations                         # how many Bellman steps
sol.apol                               # savings policy a'(a)
sol.cpol                               # consumption policy c(a)
apath, cpath = simulate(sol, 2.5, 200) # follow the policy for 200 periods from a₀ = 2.5
euler_residuals(cpath, hh)             # u'(c_t) - βR u'(c_{t+1}) along the path

simulate starts at the grid point nearest to $a_0$ and follows the indices: $i_{t+1} = \texttt{pol}[i_t]$. The path never leaves the grid. The script run/solve_infinite.jl does exactly this and prints the two checks from theory:

$ julia --project=. run/solve_infinite.jl Converged in 28 iterations; last change 4.440892098500626e-16 Contraction check: every ratio d_ℓ / d_{ℓ-1} is at most β = 0.9524; largest observed 0.9524 (few iterations because the guess is exact at the borrowing limit and paths reach it in finite time) Prediction 1: with βR = 0.981 < 1 assets drift to the limit -ϕ = -0.02 a_0 = 2.4949832775919734, a_50 = -0.02, a_200 = -0.02 Prediction 2: u'(c_t) - βR u'(c_{t+1}) ≥ 0 along the path minimum residual -0.0038; binding from t = 24

The minimum Euler residual is slightly negative, not zero. That is the grid: $a'$ can only take grid values, so the Euler equation holds only up to one grid step. Exercise 2 in the notebook asks you to show that it shrinks as $n_a$ grows.

PART 7Finite horizon and cake eating

Backward induction: solve_backward

function solve_backward(hh::Household, a, y; terminal = zeros(length(a)))
    T = length(y)                                # y[t] is income at date t
    na = length(a)
    V = zeros(eltype(a), na, T + 1)              # one column per date, plus T+1
    pol = zeros(Int, na, T)
    V[:, T + 1] .= terminal                      # Step 1: V_{T+1} = 0
    for t in T:-1:1                              # Step 2: from T back to 1
        bellman_step!(view(V, :, t), view(pol, :, t), view(V, :, t + 1), hh, a; y = y[t])
    end
    apol = a[pol]
    cpol = [y[t] + hh.R * a[i] - apol[i, t] for i in 1:na, t in 1:T]
    return FiniteSolution(collect(a), collect(y), V, pol, apol, cpol)
end
  • The same bellman_step!, called once per date. The input is column $t+1$ of V, which is already known, and the output goes into column $t$.
  • view(V, :, t) is column $t$ of the matrix itself, not a copy. When bellman_step! writes into it, it writes straight into V.
  • T:-1:1 counts down: $T, T-1, \dots, 1$.
  • No convergence check. After $T$ passes the loop ends, and the answer is exact for the grid.
  • Policies by date. pol, apol and cpol are $n_a \times T$ matrices: column $t$ is the policy at date $t$. simulate_finite(fsol, a0) follows them forward from date 1.
  • terminal is a keyword argument. Leave it out for $V_{T+1} = 0$, or pass a vector for a bequest motive (notebook exercise 3).

The cake-eating check

Never trust numerical output you have not tested. With no income, $R = 1$ and log utility, the problem has a closed form: $c_t = \dfrac{1-\beta}{1-\beta^{T-t+1}}\, a_t$. That formula is cake_eating_consumption in src/checks.jl. The script run/solve_finite.jl solves the problem on finer and finer grids and compares:

T, a0 = 20, 1.0
cake = Household(β = 0.95, R = 1.0, y = 0.0, ϕ = 0.0, γ = 1.0)   # γ = 1 is log utility
for na in (100, 400, 1600)
    a = collect(range(0.0, a0; length = na))                       # grid from 0 to the cake
    fsol = solve_backward(cake, a, zeros(T))                       # y_t = 0 at every date
    apath, cpath = simulate_finite(fsol, a0)
    exact = [cake_eating_consumption(apath[t], t, T, cake.β) for t in 1:T]
    println(na, ":  ", maximum(abs.(cpath .- exact)))
end
$ julia --project=. run/solve_finite.jl Cake eating, T = 20, a_1 = 1.0: max |c_numerical - c_closed form| by grid size na = 100: 0.00468 na = 400: 0.00149 na = 1600: 0.000338 Life cycle, T = 60: peak assets 7.53 at t = 46; terminal assets -0.02; consumption range (0.958, 1.425)

The error is not zero, and it should not be: the grid forces $a'$ onto grid points. What matters is that it falls as the grid gets finer. If it did not, the bug would be in the code, not in the grid. The last line solves a 60-period life cycle with hump-shaped income from life_cycle_income. The household saves while income is high, runs its assets down in retirement, and ends at the borrowing limit.

Testing Running tests... Test Summary: | Pass Total infinite horizon | 7 7 Test Summary: | Pass Total finite horizon reuses the Bellman step | 1 1 Test Summary: | Pass Total cake eating closed form | 3 3 Testing EC991Week2 tests passed

Each test is a prediction from theory: the savings policy is increasing, assets drift to the borrowing limit, every distance shrinks by at least $\beta$, a zero guess converges to the same $V$, one backward step from the converged $V$ reproduces it, and the cake-eating error falls with the grid. If you change the code and a test fails, you have broken something the theory says must hold.
